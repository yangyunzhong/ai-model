# 设计优先的需求交互规范

## 目标

PM/UI 原型阶段的需求交互，先确认产品设计本身：业务模块、页面、角色、流程、功能、字段、状态和体验。Mock 数据、draft API、draft 数据模型、文件落点和组件实现属于后置交接或执行内容，不应在需求确认阶段抢主线。

如果本轮原型工作会产生或修改文件、预览入口、Mock 数据或交接草案，AI 助手必须把设计交互沉淀到当前 Trellis 原型 task 的 `prd.md` 中；PM 不需要知道这个动作。

## 两段式计划

### 1. 需求交互 / 方案确认阶段

这一阶段只输出 PM 和 UI 能直接判断的内容：

- 模块边界：本次要设计哪些业务模块，哪些不做。
- 页面清单：列表页、详情页、表单页、看板页、流程页等。
- 用户角色：谁使用、谁审核、谁查看、谁维护。
- 核心功能：查询、筛选、新增、编辑、查看、确认、流转、提醒等。
- 关键字段：页面上必须出现的业务字段和展示含义。
- 状态和场景：正常、空、异常、禁用、无权限、待处理、已完成等。
- 交互动线：用户从哪里进入、先看什么、点什么、完成什么。
- PM/UI 待确认问题：只问业务、页面、流程、字段和体验问题。

这些内容同时写入或更新当前原型 task 的 `prd.md`，作为后续执行和交接的 source of truth。

不要在这一阶段展开：

- Mock 数据文件路径。
- 前端组件映射和文件落点。
- draft API 路径、方法、请求响应结构。
- draft 数据库表、字段类型、索引和关系。
- Controller、Service、Mapper、权限码、租户字段。

### 2. 执行 / 交接草案阶段

只有在 PM/UI 确认页面方案后，才展开技术交付信息：

- Mock 数据样本和统一存放位置。
- 可运行前端 Mock MVP 的文件落点。
- 页面组件映射和局部样式边界。
- draft API 协议草案。
- draft 数据库/数据模型草案。
- 开发阶段风险和待确认技术问题。

## 推荐输出模板

需求交互阶段优先使用这个模板：

```text
## 设计方案

### 模块范围
- 本次覆盖：
- 本次不覆盖：

### 页面与功能
| 页面 | 目标 | 主要功能 | 关键状态 |
| --- | --- | --- | --- |

### 用户流程
1. ...
2. ...

### 字段与状态
- 关键字段：
- 关键状态：

### 待 PM/UI 确认
1. ...
2. ...

确认后我再补执行计划，包括可运行前端 Mock、Mock 数据、draft API 和 draft 数据模型。
```

## Wrong vs Correct

### Wrong

- PM 还没确认页面方案，就先输出 `src/mock/modules/...`、接口路径和数据库表。
- 需求讨论阶段把重点放在组件、文件、API、模型，而不是页面和业务流程。
- 让 PM 判断 draft API 或 draft 数据模型是否合理。

### Correct

- 先让 PM/UI 确认模块、页面、功能、字段、状态和交互动线。
- 技术草案只作为“确认后会补”的后置交付项。
- 执行阶段再写 mock 存放位置、组件映射、draft API 和 draft 数据模型。
