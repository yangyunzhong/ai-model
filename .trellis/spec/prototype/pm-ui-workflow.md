# PM/UI 原型流程规范

## PM 入口

PM 只需要说明业务，不需要说明技术。

PM 可以提供：

- 业务背景。
- 用户角色。
- 页面清单。
- 字段名称和含义。
- 操作流程。
- 状态流转。
- 客户演示重点。
- 截图、草图、旧系统页面或参考链接。

## PM 交互边界

只向 PM 询问业务问题：

- 这个功能服务哪个业务场景？
- 哪些角色会使用？
- 客户最关心哪条演示流程？
- 页面必须出现哪些字段？
- 哪些状态、按钮或异常场景必须演示？

不要向 PM 询问技术问题：

- 用哪个前端框架？
- Node、pnpm、npm 怎么安装？
- 接口路径怎么设计？
- 数据库表怎么建？
- Controller、Service、Mapper 放哪里？
- 权限码、租户字段、数据权限怎么实现？

draft API 协议、draft 数据库/数据模型和 draft 设计开发文档由 AI 根据页面、字段、流程和状态推导，不要求 PM 直接设计。
PM 不需要判断 draft API 协议、数据库字段、索引、表关系、组件建议或开发拆分是否合理，这些交给开发阶段评审。

## UI 修正边界

UI 可以修改：

- 页面布局、密度、视觉层级和组件选择。
- 表格列顺序、字段展示、筛选区组织。
- 弹窗、抽屉、详情页、空状态、错误态和禁用态。
- 文案、按钮优先级、流程反馈和客户演示动线。
- Mock 数据的展示状态和边界样本。

UI 不应在原型阶段决定：

- 最终正式 API 路径和请求方法。
- 最终数据库表结构、索引、枚举落库方式。
- 后端权限、租户、数据权限实现。
- 正式菜单、路由、权限码和发布策略。

## 固定交接产物

原型进入执行或交接草案阶段后，必须在 `docs/prototypes/[feature-name]/` 下生成以下文件。它们是原型阶段交付给 PM、UI、开发和测试的稳定入口；信息不完整时也要生成，并在文件中保留“待确认”章节。

```text
docs
└── prototypes/
      └── [feature-name]/
          ├── prd.md
          ├── draft-api.md
          ├── draft-data-model.md
          ├── draft-design-dev.md
          └── dev-handoff.md
```

## 开始前检查

- [ ] 如果本轮会生成或修改原型产物，是否已经创建或接续 `.trellis/tasks/` 下的原型 task？
- [ ] 是否把设计方案、待确认问题和原型验收条件记录到当前 task 的 `prd.md`？
- [ ] 是否只问 PM 能回答的业务问题？
- [ ] 是否避免让 PM 选择框架、接口、数据库、脚本或 Git 流程？
- [ ] 如果还在需求交互阶段，是否先聚焦模块、页面、流程、功能、字段、状态和体验？
- [ ] 是否把 Mock 数据、draft API、draft 数据模型、draft 设计开发文档、文件落点和组件映射放到方案确认后的执行/交接阶段？
- [ ] 是否明确这是可运行前端 Mock MVP，不是正式前后端开发任务？
- [ ] 是否明确 draft API 协议、draft 数据模型和 draft 设计开发文档是交接草案，不是最终实现方案？
- [ ] 是否确认 MVP 能运行、预览和交互，而不是只有说明文档、静态文件和技术草案？
- [ ] 是否选择了 PM 最容易预览的方式？
- [ ] 是否选择了明确的前端 mock 承载位置，例如 `ruoyi-plus-vben5/` 原型区、轻量前端工程或 `prototypes/` 可运行工程？
- [ ] 是否明确交接文档固定落在 `docs/prototypes/[feature-name]/`，且不会被 `.trellis/tasks/<task>/prd.md` 或聊天记录替代？
- [ ] 是否默认使用轻量验证，并在运行 Playwright、浏览器自动化或批量截图前询问用户？

## 生成原型时

- [ ] 是否在当前 Trellis 原型 task 中记录产物位置、预览方式和验证结果？
- [ ] 页面是否能真实运行、预览和交互？
- [ ] 是否有模拟数据，而不是空壳页面？
- [ ] 是否覆盖列表、详情、新增/编辑或该业务最关键的流程？
- [ ] 是否包含正常、空、加载、错误、禁用或无权限等关键状态？
- [ ] 字段命名是否稳定，便于后续开发和测试沟通？
- [ ] 是否同步维护 `docs/prototypes/[feature-name]/prd.md`、`draft-api.md`、`draft-data-model.md`、`draft-design-dev.md` 和 `dev-handoff.md`？
- [ ] UI 是否能继续调整布局、视觉层级、文案和演示动线？
- [ ] 如果未运行自动化浏览器验证，是否记录了预览地址和手动检查路径？

## 不要提前做

- [ ] 不在原型确认前拆正式开发任务；原型 task 只用于保存原型需求、上下文和产物记录。
- [ ] 不把 draft API 当成正式 API。
- [ ] 不把 draft 数据模型当成正式数据库表设计。
- [ ] 不把 draft 设计开发文档当成正式前端架构或开发任务拆分。
- [ ] 不在原型确认前修改后端工程。
- [ ] 不把 Mock 数据说成真实接口已经完成。

## 确认原型时

- [ ] PM 是否确认业务目标表达正确？
- [ ] PM 是否确认字段和流程正确？
- [ ] UI 是否确认主要页面状态和体验可接受？
- [ ] 客户演示路径是否顺畅？
- [ ] 是否没有要求 PM 评审 draft API、draft 数据模型或 draft 设计开发文档的技术合理性？
- [ ] 待确认问题是否记录在原型说明或交接包里？

## 原型确认后的交接

原型确认后再整理开发交接包。交接包应包含：

- `docs/prototypes/[feature-name]/prd.md`：原型 PRD、业务目标、页面清单、角色、字段、流程、状态和验收条件。
- 页面清单和路由建议。
- 字段说明、字段来源和是否必填。
- Mock 数据样例和状态流转。
- 用户操作流程和异常场景。
- `docs/prototypes/[feature-name]/draft-api.md`：候选接口、方法、路径、请求参数、响应结构、错误状态和权限/租户提示。
- `docs/prototypes/[feature-name]/draft-data-model.md`：候选实体、表、字段、关系、状态枚举、索引和数据权限风险。
- `docs/prototypes/[feature-name]/draft-design-dev.md`：页面结构、用户流程、关键状态、前端 mock 实现说明、组件/交互建议、开发拆分建议、验收点和实现风险。
- `docs/prototypes/[feature-name]/dev-handoff.md`：预览入口、产物路径、验证结果、开发接手注意事项和待确认问题。
- 权限、租户、数据权限、导入导出等实现风险。
- 待业务、开发或测试确认的问题。

正式开发接手后，再读取 `../guides/ruoyi-plus-vben5-contract-guide.md` 对齐前后端契约。
