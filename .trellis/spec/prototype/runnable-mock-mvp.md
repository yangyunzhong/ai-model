# 可运行前端 Mock MVP 规范

## 产物定义

PM/UI 阶段的产物是**真实可运行的前端 Mock MVP**，不是只写说明文档，也不是只把静态文件放到 `prototypes/`。

这个阶段的目标是让 PM、UI、客户和开发尽早看到页面、流程、字段、状态和交互是否表达了真实业务，同时沉淀 draft 级 API 协议、数据库/数据模型设计和设计开发文档。它不负责最终正式后端接口、数据库、权限、租户、菜单、前端架构或工程分层设计。

可运行前端 MVP 是原型阶段第一质量门槛。draft API 协议、draft 数据模型和 draft 设计开发文档不能阻塞 PM 预览；如果当前技术方案跑不起来，AI 助手必须改选能运行的前端 mock 方案，不能用不可运行的静态文件替代。

## 适用范围

使用本规范的场景：

- PM 用自然语言提出业务目标、页面、字段、流程或客户演示诉求。
- UI 需要基于 PM 原型调整布局、视觉层级、组件状态和交互细节。
- 需要生成可预览的后台管理类前端 Mock MVP。
- 原型尚未确认，不能提前进入正式开发设计。
- 原型请求会产生或修改文件、预览入口、Mock 数据、交接草案或验证记录，需要进入 Trellis 原型 task。

不使用本规范的场景：

- 已确认原型并开始正式前后端开发。
- 需要定义最终真实 API、数据库表、权限码、租户隔离或数据权限。
- 需要修改 `RuoYi-Vue-Plus/` 后端代码。

## 产物契约

每个 PM/UI Mock MVP 必须包含：

- 可运行前端预览入口：本地 URL、启动命令、端口和必要环境说明。
- 页面清单：列表、详情、新增/编辑、流程页、看板或其他业务页面。
- 模拟数据：字段稳定、能覆盖主要业务状态，不伪装成真实接口已完成。
- 页面状态：正常、空状态、加载态、错误态、无权限或禁用态。
- 核心交互：查询、筛选、切换状态、打开详情、新增/编辑、提交反馈。
- 原型说明：业务目标、角色、字段含义、流程说明和待确认问题。
- 原型文档产物：固定放在 `docs/prototypes/[feature-name]/`，包含 `prd.md`、`draft-api.md`、`draft-data-model.md`、`draft-design-dev.md` 和 `dev-handoff.md`。
- draft API 协议设计：写入 `draft-api.md`，记录候选接口、方法、路径、请求参数、响应结构、错误状态和权限/租户提示。
- draft 数据库/数据模型设计：写入 `draft-data-model.md`，记录候选实体、表、字段、关系、状态枚举、索引和数据权限风险。
- draft 设计开发文档：写入 `draft-design-dev.md`，记录页面结构、用户流程、关键状态、前端 mock 实现说明、组件/交互建议、开发拆分建议、验收点和实现风险。
- 开发交接说明：写入 `dev-handoff.md`，明确 draft 不等于最终实现方案，开发阶段需要重新评审。
- Trellis task 记录：当前任务的 `.trellis/tasks/<task>/prd.md` 中保留设计方案、验收条件、产物位置、验证记录和待确认问题；它不替代 `docs/prototypes/[feature-name]/prd.md`。

固定文档目录：

```text
docs
└── prototypes/
      └── [feature-name]/
          ├── prd.md
          ├── draft-api.md
          ├── draft-data-model.md
          ├── draft-design-dev.md
          └── dev-handoff.md
```

如果业务细节、字段、流程、权限、租户或技术判断尚未完整确认，也必须生成上述文件，并在对应文件中用“待确认”章节标注缺口；不要因为草案不完美而跳过产物。

## 推荐承载位置

如果需要贴近正式后台体验，可在 `ruoyi-plus-vben5/` 中使用明确的原型区，避免污染正式业务模块：

```text
ruoyi-plus-vben5/apps/web-antd/src/views/prototypes/<feature-name>/
ruoyi-plus-vben5/apps/web-antd/src/mock/modules/<domain>/<feature-name>.ts
```

业务 Mock 数据必须统一放在 `apps/web-antd/src/mock/modules/` 下，并按模块划分子目录或文件。页面目录只保留视图组件和必要 adapter，不长期存放 seed data 或大段前端模拟服务。

如果选择独立承载，`prototypes/` 应是可运行前端 mock 工程目录，而不是静态文件堆放目录；文档交接产物仍固定放在 `docs/prototypes/[feature-name]/`：

```text
prototypes/
└── <feature-name>/
    ├── README.md
    ├── package.json
    ├── src/
    └── mock-data/
```

不要用 `prototypes/<feature-name>/draft-api.md`、`prototype-notes.md` 或聊天记录替代 `docs/prototypes/[feature-name]/` 下的固定文档产物。

不要在 PM/UI 原型阶段修改 `RuoYi-Vue-Plus/`。确需开发介入时，先完成原型确认和交接包，再进入正式开发任务。

## Mock 数据规则

- 使用 `ruoyi-plus-vben5/` 承载原型时，Mock 数据统一进入 `apps/web-antd/src/mock/modules/<domain>/`。
- 字段命名要稳定，便于 PM、UI、开发和测试共同讨论。
- 列表型页面至少准备正常数据、空数据和异常/边界数据。
- 状态字段要覆盖主要业务流转，不只保留单一成功态。
- 所有 Mock 数据都应能被替换成真实接口数据，不把页面写死成截图式展示。
- 原型说明中必须标明哪些数据是 Mock，哪些字段仍待 PM 或业务确认。

## Draft API 协议规则

- 根据页面、字段、流程和状态推导候选接口，不要求 PM 直接设计接口。
- PM 不需要判断候选接口协议是否合理。
- 至少记录接口目的、候选方法、候选路径、请求参数、响应结构和错误状态。
- 如涉及权限、租户、数据权限、导入导出或字典枚举，只记录风险和建议，不下最终结论。
- draft API 协议必须标注为草案，不能声称接口已完成、已联调或后端已实现。

## Draft 数据模型规则

- 根据页面字段、Mock 数据和业务状态推导候选实体、表、字段和关系。
- PM 不需要判断候选表结构、字段类型或索引是否合理。
- 至少记录主对象、关键字段、状态枚举、关联关系和可能索引。
- 如涉及租户字段、数据权限字段、逻辑删除、审计字段或唯一约束，只记录开发阶段需要确认的建议。
- draft 数据模型不是正式 DDL、迁移脚本或最终数据库设计。

## Draft 设计开发文档规则

- 根据可运行原型、页面字段、流程状态和 Mock 数据整理设计开发草案，不要求 PM 直接设计开发方案。
- PM 不需要判断组件选型、开发拆分、工程落点或技术风险是否合理。
- 至少记录页面结构、用户流程、关键状态、前端 mock 实现说明、组件/交互建议、开发拆分建议、验收点和实现风险。
- 如涉及正式路由、菜单、权限、组件封装、接口联调或测试回归，只记录开发阶段需要确认的建议。
- draft 设计开发文档不是正式前端架构、开发任务拆分或最终实现方案。

## 实现规则

- 优先选择 PM 能最快看到效果的可运行前端方案：复用已有前端、明确的前端原型区或轻量 Vue/Vite mock 工程。
- AI 助手负责探测环境并选择方案，不要求 PM 理解 Node、依赖安装、端口或脚本。
- 可以参考 `ruoyi-plus-vben5/` 的后台风格，但不要默认把原型写进正式业务模块。
- 原型阶段可以使用本地数组、JSON 文件或轻量 mock 服务。
- 不要把 mock 请求包装成“真实接口已联调完成”。
- 原型确认前必须允许创建 Trellis 原型 task 来保存上下文，但不要拆正式开发任务。
- 不要把 draft API 协议、draft 数据模型或 draft 设计开发文档当成正式实现承诺。

## 验证要求

交付 PM/UI 原型前至少确认：

- 预览入口可用，页面不是空白，并且有明确启动命令或本地 URL。
- 主流程能点击走通。
- 关键字段、按钮和状态能看到。
- 移动端或窄屏不出现明显文字重叠；后台类原型至少保证常用桌面宽度可用。
- 控制台没有影响主流程的明显运行错误。
- `docs/prototypes/[feature-name]/` 下的 `prd.md`、`draft-api.md`、`draft-data-model.md`、`draft-design-dev.md` 和 `dev-handoff.md` 已生成，并包含预览入口、Mock 数据位置、页面清单、draft 技术草案和待确认问题。
- PM 确认项只包含业务、页面、字段、流程和状态；draft 技术设计由开发评审。

默认只做轻量验证：

- 确认服务能启动或已有可访问预览地址。
- 给出 PM 可以手动打开的 URL 和主要检查路径。
- 记录未做自动化浏览器验证的原因，例如“PM 原型阶段默认轻量验证”。

Playwright、浏览器自动化截图、多视口截图和视频录制属于增强验证，不默认执行。只有在以下场景才执行：

- 用户明确要求自动化验证或截图。
- 原型准备给客户正式演示，且用户同意增加验证耗时。
- AI 判断存在明显布局风险、页面空白风险或关键流程风险，并先询问用户是否运行自动化验证。

询问用语应简短，例如：“是否需要我跑 Playwright 自动化验证并保存截图？会更耗时；不跑的话我给你预览地址和手动检查路径。”

如果用户未同意，不要自动跑 Playwright，也不要批量生成截图。

## Wrong vs Correct

### Wrong

- PM 提一个页面需求，AI 先拆 Controller、Service、Mapper 和数据库表。
- 原型只输出说明文档或静态文件，没有可运行前端。
- Mock 页面直接写入正式业务模块，并声称接口已经完成。
- draft API 协议、draft 数据模型或 draft 设计开发文档被写成最终设计，没有草案标记和待确认项。
- 让 PM 选择 Node 版本、包管理器、接口路径或表结构。

### Correct

- PM 提业务诉求后，AI 先生成可运行、可预览、可交互的前端 Mock MVP。
- UI 基于可运行页面调整布局、状态和演示动线。
- Mock 数据清晰标注，字段稳定，状态覆盖主要流程。
- 同步输出 draft API 协议、draft 数据模型和 draft 设计开发文档，明确它们只是开发交接草案。
- 原型确认后，由开发按正式技术栈评审并重做或调整 API、数据库、权限和工程结构。
